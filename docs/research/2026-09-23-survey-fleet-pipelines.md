## 1. Anthropic's own reference (baseline, not a deployment story)

**Anthropic | https://code.claude.com/docs/en/monitoring-usage | official docs, current as of Sept 2026**

- Pipeline: Claude Code (producer) to OTLP (metrics/logs/traces, gRPC or HTTP) to any OTLP collector/backend (transport is generic; Anthropic doesn't run the store).
- Identity: `user.id` (random anonymous, persisted in `~/.claude.json`), `user.email` and `organization.id` are included **by default** when authenticated (not hashed, not opt-in). `user.account_uuid`/`account_id` gated by `OTEL_METRICS_INCLUDE_ACCOUNT_UUID` (default true). No built-in hashing/anonymization option exists, so orgs must redact downstream.
- Content: prompts and tool details are **redacted by default**; opt-in flags: `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_ASSISTANT_RESPONSES`, `OTEL_LOG_TOOL_DETAILS`, `OTEL_LOG_TOOL_CONTENT`, `OTEL_LOG_RAW_API_BODIES` (full Messages API JSON), `OTEL_LOG_MANAGED_SETTINGS` (redacted settings plus SHA-256 digest).
- Managed-settings env blocks **lock** the OTLP destination org-wide and strip conflicting per-developer overrides (endpoint/protocol/headers).
- Metrics: `claude_code.session.count`, `.lines_of_code.count`, `.pull_request.count`, `.commit.count`, `.cost.usage`, `.token.usage`, `.code_edit_tool.decision`, `.active_time.total`. Events: `user_prompt`, `assistant_response`, `tool_result`, `tool_decision`, `api_request`, `api_error`, `managed_settings_resolved`. Correlation via `prompt.id` and `event.sequence`.
- Useful because every vendor/org guide below cites this schema verbatim; it's the shared vocabulary, not a deployment case study.

## 2. Organizations describing their own fleet deployment

### Intercom (Brian Scanlan, Senior Principal Engineer): the clearest verified "Intercom shape" match

**Primary source, first-party: https://ideas.fin.ai/p/how-we-use-claude-code-today-at-intercom | March 19, 2026**
**Companion post: https://ideas.fin.ai/p/we-gave-claude-code-to-everyone-at | March 23, 2026**
(Secondary coverage, same interview, cross-checked: https://www.lennysnewsletter.com/p/how-intercom-2xd-their-engineering (Apr 20, 2026) and https://www.chatprd.ai/how-i-ai/how-intercom-doubled-engineering-output-brian-scanlan-ai-workflows-for-claude-code (Apr 19, 2026))

- **Pipeline**: Claude Code lifecycle hooks (SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, PermissionRequest, SubagentStart, SessionEnd, etc., 14 event types total) to OpenTelemetry to **Honeycomb** (skill/tool usage, cost, adoption dashboards). Separately, full session transcripts sync to **S3** for durable storage/replay. On `SessionEnd`, a hook feeds the whole session transcript to **Claude Haiku** as an LLM judge that auto-classifies improvement gaps (`missing_skill`, `missing_tool`, `repeated_failure`, `wrong_info`) and posts a pre-filled GitHub issue link to Slack, closing the loop "real sessions to detected gaps to GitHub issues to new skills to better sessions."
- **Identity handling**: explicit "privacy-first" stance: Intercom states it **never** captures user prompts, messages, or tool input in the Honeycomb/OTel stream. For the S3 transcript archive, usernames are **SHA-256 hashed** before storage (not clear-text, not full anonymization of session content).
- **Content captured**: skill invocation, tool names, session metadata, durations, not prompt/tool-argument content in the telemetry path. The archived S3 transcripts are the richer artifact, used only by the automated Haiku judge and internal tooling, not broadcast in cleartext dashboards.
- **Scale**: 100% of engineers shipping via Claude Code; rollout later extended to non-engineers, over 1,000 people with access, 300+ weekly active users, 60% of Director+ active. Merged PRs per R&D headcount **2x in 9 months**.
- **Dashboards**: peer-comparison dashboards showing engineers percentile rank vs. others; a "2x Portal" (Streamlit) tracking merged-PRs-per-R&D-head; skill-usage leaderboards. Top skills: creating PRs, internal admin tooling, querying Snowflake logs, CI troubleshooting.
- **Lessons/numbers**: (1) an LLM judge run over "months and months" of PR-description data found AI-generated PR description quality **degrading over time**, prompting workflow enforcement, a concrete example of using an LLM judge for regression detection, not just one-off scoring. (2) A shared Honeycomb API key deployed to all developer laptops keeps the skill-telemetry integration nearly zero-config. (3) Culture point repeatedly stressed: engineers needed *permission* (to hit Snowflake, ship from a phone, bypass email verification for internal tools) more than documentation; telemetry was what let leadership grant that permission safely.
- This is, on the evidence gathered, the fullest **verified** public description of an "Intercom-shape" pipeline: hooks plus OTel plus S3 transcript archive plus LLM-judge analysis, run by the org itself, not a vendor.

### Bindplane (dogfooding their own product on their own engineering org)

**https://bindplane.com/blog/claude-code-observability-at-scale-how-we-did-it-with-bindplane | June 4, 2026 | Chelsea Wright, Adnan Rahic**
**https://bindplane.com/blog/claude-code-monitoring-at-scale-gateways-and-routing-with-opentelemetry | July 9, 2026 | Adnan Rahic**

- Pipeline: Claude Code (managed `settings.json`, `CLAUDE_CODE_ENABLE_TELEMETRY=1`, OTLP/gRPC to `127.0.0.1:4317`) to a **BDOT (Bindplane Distro for OTel) Collector deployed via MDM to every developer laptop** (edge tier, redacts `user.email` and other sensitive fields at source) to a centralized cloud BDOT gateway that conditionally routes signals by type to fan-out into **Google Cloud Monitoring** (redacted metrics/dashboards), **Google Cloud Storage** (full, unredacted audit trail) and **Swarmia** (dev-experience/PR-throughput correlation). The second post describes splitting further: cost/token metrics to Cloud Monitoring, event streams (`tool_decision`, `tool_result`, `api_request`) to **Dynatrace** as system-of-record, everything else falls through to Dynatrace too.
- Identity: SSO shared between Claude web console and Claude Code; edge collector strips/redacts `user.email` before the gateway; destination credentials live only on the gateway, not on developer machines.
- Content: four tracked signal areas: model usage/cost, tool usage/rejection, prompt-plus-response audit trail (kept in the unredacted GCS copy only), and approved tool calls (flagged as "highest-risk surface").
- Scale: "organization-wide" rollout, no headcount given.
- Lessons: (1) "The agent's job is to collect and redact. The gateway's job is to decide and deliver," meaning push redaction to the edge, routing logic to a central gateway. (2) Gateway must run redundantly behind a load balancer in production; a single-VM gateway is a real bottleneck/SPOF they hit. (3) "Misrouted data fails silently": they explicitly call out needing a live routing-preview to catch conditional-routing mistakes before they become invisible data loss. (4) Manage cardinality via Claude Code's own telemetry flags at the source rather than filtering downstream.

### Anonymized "30-developer shop" case study (vendor-published, company not named, flagged as unverifiable-as-named-org)

**https://www.digitalapplied.com/blog/case-study-claude-code-team-adoption-30-dev-shop-2026 | May 15, 2026 | Digital Applied**

- Not a named company (client anonymized), so it cannot be added to the "who has done this" list, but the operational lesson is concrete and reusable: their **v1 adoption dashboard tracked vanity metrics that license telemetry already covered** (sessions opened, tokens spent, average session length) and "read flat for six weeks even as underlying capability visibly shifted." They rebuilt it around skill-library breadth/depth, time-to-first-meaningful-output (-45% for new hires), PR-to-merge delta (-18% for Claude-assisted PRs), and an audit-log-derived score, aggregated at squad level (6 squads x 5 devs), not per-engineer, for privacy.
